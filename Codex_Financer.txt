2. OBJETIVO DE FINANCER

Aplicación web personal para registrar y consultar patrimonio, liquidez,
inversiones, posiciones, rentabilidad, resultados y, más adelante, gastos y
objetivos. Debe servir desde ordenador y móvil, ser sencilla y mantener coste
monetario cero. El propietario no tiene conocimientos de programación.

El registro será manual o mediante automatismos internos. No conectar bancos,
brokers ni cuentas de inversión mediante APIs. Mantener la arquitectura HTML,
CSS y JavaScript con Supabase y alojamiento estático, salvo acuerdo posterior.
No cambiar de framework por iniciativa propia ni contratar servicios.

El objetivo inmediato es registrar y consultar posiciones abiertas y activas.
No reconstruir operaciones del pasado que ya no estén activas. Qué hacer con
una posición que se cierre en el futuro se decidirá al abordar Resultados:
no está acordado eliminarla ni conservarla automáticamente.

3. ESTRUCTURA FUNCIONAL ACORDADA

Financer
|-- Patrimonio total
|   |-- Liquidez
|   |   |-- Cuentas bancarias (estructura prevista)
|   |   `-- Efectivo (estructura prevista)
|   `-- Inversiones
|       |-- Bolsa
|       |-- Crypto
|       |   |-- Pools de Liquidez -> Plataforma -> Red -> Par
|       |   |-- Hold -> Red -> Crypto
|       |   |-- Farmeo DEX -> Plataforma -> Trade
|       |   `-- Shorts -> Plataforma -> Red -> Trade
|       |-- Préstamos
|       `-- Cuentas remuneradas
|-- Resultados
|-- Gastos
`-- Objetivos

Este árbol recoge la intención acordada; no certifica que todos sus apartados
ya estén creados como registros en la cuenta del propietario.

Los niveles son variables: no imponer una profundidad fija a todas las ramas.
Crypto es particular y cada estrategia tiene su propio recorrido. Los niveles
Plataforma y Red no son obligatorios para todas las estrategias.
Debe ser posible añadir más categorías y subcategorías; una futura estrategia
puede requerir campos o cálculos nuevos, que se diseñarán cuando corresponda.

Una plataforma se registra una sola vez y podrá utilizarse en varias categorías
y estrategias. No duplicarla por aparecer en distintos menús. Las plataformas
son entidades independientes de las categorías; no convertirlas en copias de
subcategorías para aparentar un árbol completo.

Trade significa una operación individual con apertura y cierre, tanto en
Farmeo DEX como en Shorts. El propietario ha indicado que no necesita varias
posiciones independientes sobre el mismo activo/par dentro de la misma
combinación de estrategia, plataforma y red, cuando esos niveles correspondan.
La identidad exacta de cada posición todavía debe concretarse al diseñar sus
formularios; no imponer una restricción única sobre el nombre sin acordarlo.

Mantener los nombres elegidos: Patrimonio total, Liquidez, Inversiones, Bolsa,
Crypto, Préstamos, Cuentas remuneradas, Resultados, Gastos y Objetivos.

7. ORGANIZACIÓN ACTUAL DEL CÓDIGO

index.html:
Estructura de pantallas, acceso, menú, ruta, mensajes y editor. Carga los scripts
explícitamente en orden. No necesita compilación.

css/estilos.css:
Presentación responsive, formularios, mensajes, estados de foco y pantallas móviles.
Se conservó el diseño base; no se hizo un rediseño visual completo.

js/supabase-config.js:
Crea el cliente de Supabase con la URL y clave pública del proyecto. Si el CDN
no está disponible, permite mostrar un error recuperable. No contiene claves privadas.

js/modelo.js:
Funciones independientes del navegador y la base de datos. Construye el árbol,
obtiene rutas, valida nombres/duplicados y sanea navegación. Usa recorridos
iterativos para no depender de la pila de llamadas en árboles profundos.
Las raíces Liquidez e Inversiones se localizan por sus nombres normalizados;
la interfaz las protege de edición y borrado. Un identificador funcional que no
dependiese del nombre requeriría un diseño de esquema posterior.

js/estrategias.js:
Describe los cuatro recorridos Crypto acordados. Es un contrato de extensión:
NO implementa todavía los formularios ni el recorrido completo Plataforma/Red/Posición.

js/datos.js:
Repositorio al que se inyectan el cliente Supabase y el ID del usuario verificado.
Lee categorías y plataformas en páginas de 500 filas y confirma las escrituras
con select(...).single(). Envía propietario en las creaciones y filtra por él
las lecturas y modificaciones. Las políticas del servidor siguen siendo la
protección efectiva; los filtros del frontend no sustituyen RLS.

js/interfaz.js:
Construye las pantallas, la navegación y las operaciones de categorías/plataformas.
Actualiza la copia local con la fila que confirma el servidor. Respeta los errores
de relaciones y no elimina en cascada. No tiene formularios financieros de posiciones.

js/acceso.js:
Comprueba el usuario con getUser(), gestiona acceso/salida y reintentos, atiende
cambios de sesión y descarta respuestas obsoletas. Las consultas nuevas se difieren
fuera del callback de Auth para evitar bloqueos. No vuelca datos privados a consola.

Los scripts se encapsulan y exponen interfaces en globalThis.Financer. Se retiraron
las colecciones y funciones globales sueltas que mezclaban responsabilidades.

Otros archivos:
- package.json y package-lock.json: herramientas de desarrollo reproducibles.
  Node >=20; SDK de pruebas Supabase 2.95.3; Playwright 1.62.1.
  Node no es necesario para servir la aplicación estática.
- scripts/check-js.cjs: revisión de sintaxis.
- tests/modelo.test.cjs y tests/datos.test.cjs: 11 pruebas de modelo y repositorio.
- tests/browser.cjs: SDK real con toda la red interceptada y API ficticia.
- .github/workflows/comprobaciones.yml: comprobaciones de desarrollo y propuestas.
- docs/Arquitectura.md: diseño técnico y acuerdos funcionales.
- docs/Verificacion.md: comprobaciones manuales numeradas.
- AGENTS.md: instrucciones de trabajo para Codex.
- Control_Cambios.md: resumen de entregas y recuperación.

8. BASE DE DATOS: QUÉ SE VERIFICÓ Y QUÉ NO

Durante la fase técnica se pudo acceder al proyecto que coincide con la URL del
frontend y se inspeccionó su estructura en lectura. Existen estas tablas:
- bloques: categorías con ID, propietario, nombre y padre opcional.
- plataformas: catálogo compartido por usuario.
- productos: bloque_id, plataforma_id opcional, nombre y configuracion JSON.
- movimientos: operaciones asociadas a productos, con fecha/tipo/importe/moneda/detalles.

La existencia de productos y movimientos en el esquema NO significa que sus
formularios estén implementados en la aplicación.

Las cuatro tablas tienen RLS activada y políticas de lectura, creación, actualización
y eliminación por usuario_id. UPDATE tiene USING y WITH CHECK. La propiedad tiene
valor por defecto auth.uid(). Hay relaciones ON DELETE RESTRICT que evitan borrar
categorías/plataformas/productos con elementos dependientes. Los triggers comprueban
la propiedad de las relaciones y evitan ciclos entre categorías, sin SECURITY DEFINER.

Se realizó una transacción de solo lectura con rol authenticated y un sujeto
ficticio: no vio registros de ninguna de las cuatro tablas. No se crearon cuentas
ni se hicieron escrituras sobre los registros reales para probar el frontend.
La autenticación y persistencia con la cuenta del propietario siguen pendientes
de comprobación manual. No afirmar que se probaron dos cuentas reales.

No se han ejecutado migraciones, cambiado permisos ni hecho restauraciones.
Los futuros campos específicos de producto pueden aprovechar configuracion JSON,
preservando propiedades desconocidas, pero deben diseñarse antes de escribirlos.
No convertir ese objeto en sustituto de las relaciones y reglas de integridad.
La comprobación de duplicados de nombre es local: no garantiza exclusión entre
pestañas concurrentes. No se añadió una restricción SQL única sin estudiar los datos.
